# 双类型 AI 审核设计

## 背景

报告中心当前将批次生成的初始报告和用户上传的修订报告交给同一种异步审核任务。Worker 始终读取一套全局启用提示词，并把一组全局业务检查点注入模型输入。这无法表达两类审核目标：初始报告只需要基础质量检查，修订报告需要独立的性能容量深度审核。

本设计将审核明确分为“初始审核”和“修订审核”，共用一个模型连接配置，分别维护两套版本化提示词。业务检查点退出未来审核流程，但历史数据继续保留。

## 目标

- 批次登记的初始报告只执行初始审核。
- 用户上传的新版本只执行修订审核，不重复初始审核规则。
- 模型 URL、Model Name 和 API Key 由两种审核共用。
- 初始审核提示词和修订审核提示词分别版本化。
- 每条审核记录固定审核类型和实际使用的提示词版本。
- 重新审核沿用原审核类型。
- 审核输出继续使用中文 Markdown，不要求 JSON。
- 保留历史审核、旧检查点快照和旧提示词引用的可读性。

## 非目标

- 不审核图片、截图或图表图片的视觉语义。
- 不在本期实现可编排的多阶段审核工作流。
- 不按系统、报告模板或用户动态选择提示词。
- 不自动修改 DOCX 文件。
- 不在本次迁移中物理删除旧检查点表或历史字段。

## 领域术语

### 初始审核

初始审核只作用于批次生成的初始版本，审核类型值为 `initial`。它关注错别字、病句、目录与标题结构一致性、章节缺失、空章节、编号和基础表格完整性。

### 修订审核

修订审核只作用于用户上传版本，审核类型值为 `revision`。它关注性能容量指标、跨章节数据一致性、结论依据、风险识别和建议可执行性，不重复初始审核规则。

### 共用模型配置

两种审核共用一份模型连接配置，包括 API URL、Model Name 和 API Key。提示词不再携带独立模型连接信息。

## 方案比较

### 方案一：审核类型显式建模（采用）

审核任务和提示词都保存 `audit_type`，Worker 按审核类型读取对应提示词。该方案能稳定支持重试、历史回放、数据修复和页面展示。

### 方案二：根据报告版本临时推断

Worker 根据 `version_type` 选择提示词。改动较少，但审核记录本身没有类型，重新审核和历史查询依赖外部推断，容易产生语义漂移。

### 方案三：通用审核工作流

建立阶段、规则集和执行编排表。扩展性更强，但当前只有两个固定入口，复杂度和维护成本不合理。

## 数据模型

### 共用模型配置表

新增 `capability_report_ai_config`，第一版只维护一条有效配置：

| 字段 | 说明 |
| --- | --- |
| `id` | 配置 ID |
| `api_url` | 兼容 Chat Completions 的基础 URL |
| `model_name` | 模型名称 |
| `api_key` | API Key，接口永不返回明文 |
| `create_time` | 创建时间 |
| `update_time` | 更新时间 |

模型配置更新采用原记录更新，不单独版本化。审核记录继续保存本次执行的 `model_name`，历史记录不保存 API Key。

### 提示词表

`capability_report_audit_prompt` 增加：

| 字段 | 说明 |
| --- | --- |
| `audit_type` | `initial` 或 `revision` |

每种审核类型只能有一个启用版本。保存提示词时只停用同类型的旧版本，另一种审核类型不受影响。历史 `prompt_id` 和 `prompt_version` 继续有效。

现有 `model_name`、`api_url`、`api_key` 字段暂时保留以兼容旧数据，但新代码不再从这些字段读取连接配置。

### 审核记录表

`capability_report_audit` 增加：

| 字段 | 说明 |
| --- | --- |
| `audit_type` | 本次审核固定类型：`initial` 或 `revision` |

创建审核记录时必须写入类型，Worker 不根据版本号临时判断。历史记录按关联版本回填：初始版本回填 `initial`，上传版本回填 `revision`。

### 旧检查点数据

`capability_report_audit_checkpoint`、`checkpoint_snapshot` 和旧 `result_data` 不删除。新任务不再读取检查点、不再写入检查点快照，历史接口仍可返回已有数据。

## 任务创建与执行

### 批次登记

`POST /reports/register` 和 `POST /reports/register-upload` 创建初始版本后，创建 `audit_type = initial` 的审核记录。

### 用户上传

`POST /reports/{reportId}/versions` 创建上传版本后，创建 `audit_type = revision` 的审核记录。

### 重新审核

重新审核先读取该版本最近一条审核记录的 `audit_type`，新审核记录沿用该类型。若旧数据没有类型，则仅作为兼容逻辑根据 `version_type` 推导一次，并写入新记录。

### Worker

Worker 执行顺序：

1. 领取一条 `pending` 审核记录，同时读取 `audit_type`。
2. 读取共用模型连接配置。
3. 按 `audit_type` 读取对应启用提示词。
4. 解析 DOCX 并构造审核输入。
5. 调用模型并流式记录审核过程。
6. 保存 Markdown 原文、结论、提示词 ID、提示词版本和模型名称。

任意配置缺失时任务进入 `error`，错误信息明确指出缺少模型配置、初始审核提示词或修订审核提示词。

## DOCX 审核输入

当前解析器只返回正文字符串和表格，无法可靠判断目录与标题层级。初始审核需要补充以下结构化输入：

- `paragraphs`：保留现有正文数组，兼容当前逻辑。
- `headings`：标题文本、标题级别和原始样式名。
- `tocEntries`：能从 DOCX 目录字段或目录段落中提取的目录项。
- `tables`：保持现有二维单元格数据。
- `scope`：明确文字、表格和结构可审核，图片与图表语义不可审核。

目录无法读取或文档未更新目录域时，模型必须说明“无法确认目录一致性”，不能编造通过结论。

## 默认提示词

### 初始审核提示词

```text
你是性能容量报告的初始质量审核助手。你只审核批次生成的初始 DOCX 报告，目标是发现基础文字和文档结构问题。

审核范围仅包括系统提供的报告基本信息、正文文字、标题层级、可读取的目录条目和表格文字。不要判断图片、截图或图表图片的视觉语义，不要声称检查了字体、颜色、分页、对齐等未提供的版式信息。

请检查：
1. 报告标题、系统名称、报告月份等基本信息是否前后一致。
2. 可读取的目录条目与正文标题是否存在缺失、多余、顺序错误或编号不一致。
3. 章节和子章节是否缺失、重复、为空或只有标题没有正文。
4. 正文是否存在明显错别字、病句、标点错误、术语混用或同一名称前后不一致。
5. 表格标题、表头、单位和单元格内容是否存在明显缺失或前后不一致。
6. 文档中是否存在明显占位符、测试文字、未替换模板内容或无法解释的空值。

只根据输入中可读取的内容判断。证据不足时明确说明无法判断，不得编造文档内容。发现问题时指出原文位置或相关章节，并给出可执行的修改建议。
```

### 修订审核提示词

```text
你是性能容量报告的修订审核助手。你只审核用户上传的修订版本，目标是判断性能容量分析、数据结论和治理建议是否合理。不要重复执行错别字、目录一致性等初始质量检查。

审核范围仅包括系统提供的报告基本信息、正文文字、表格数据和标题结构。不要判断图片、截图或图表图片的视觉语义。

请检查：
1. 性能指标、容量指标、阈值、统计周期和单位是否明确，最小值、最大值、平均值或关键指标为 0 时是否有合理解释。
2. 系统概述、组件清单、服务器数量、性能分析小结和结论中的数量是否前后一致。
3. 各组件是否都有对应的性能或容量分析，是否存在只有数据没有分析、只有结论没有依据的情况。
4. 报告结论是否能由正文或表格中的数据支撑，是否存在数据与结论矛盾、统计口径不一致或推导跳跃。
5. 是否识别容量瓶颈、资源风险、趋势变化和影响范围，风险等级是否与证据匹配。
6. 扩容、优化或治理建议是否具体可执行，是否包含对象、依据、优先级或验证方式。
只根据输入中可读取的内容判断。证据不足时明确说明无法判断，不得编造指标、服务器数量或图表结论。发现问题时引用相关章节或表格依据，并给出可执行的修改建议。
```

模型客户端统一附加输出协议：首行必须为“审核结论：通过”或“审核结论：不通过”，后续使用中文 Markdown 输出审核总结、发现的问题和修改建议，不输出 JSON。提示词编辑者无需重复维护输出协议。

## API 设计

### 共用模型配置

- `GET /api/report-management/ai-config`
- `PUT /api/report-management/ai-config`

GET 返回脱敏 Key；PUT 中 Key 留空表示沿用当前值。

### 两类提示词

- `GET /api/report-management/audit-prompts/initial/active`
- `POST /api/report-management/audit-prompts/initial`
- `GET /api/report-management/audit-prompts/revision/active`
- `POST /api/report-management/audit-prompts/revision`

POST 每次创建新版本并启用。服务端拒绝未知审核类型。

旧 `GET /audit-prompts/active` 和 `POST /audit-prompts` 暂时保留兼容，映射到修订审核提示词，并在服务端标记为弃用。

### 审核响应

报告详情、审核详情和审核会话响应增加：

```json
{
  "auditType": "initial",
  "auditTypeLabel": "初始审核"
}
```

报告列表不新增审核类型列。

## 前端设计

AI 审核配置页调整为：

1. 顶部“模型连接配置”，统一维护 URL、Model Name 和 API Key。
2. 下方“初始审核提示词”和“修订审核提示词”两个页签。
3. 每个页签显示当前版本、用途说明、提示词编辑器和“保存为新版本”。
4. 移除业务检查点页签、检查点统计和检查点组合说明。

报告详情和审核工作台显示审核类型标签。报告列表继续通过版本类型和最新审核状态表达主流程，不增加额外列。

## AI 对话

审核工作台中的 AI 对话与具体审核记录关联。Agent 使用该审核记录的 `prompt_id` 对应提示词作为上下文；如果历史记录没有提示词引用，则按审核类型读取当前启用提示词。模型连接始终读取共用配置。

## 数据迁移

迁移脚本必须兼容 MySQL 5.7，并可重复执行：

1. 创建共用模型配置表。
2. 从当前启用提示词复制 URL、Model Name 和 API Key 到共用配置；不存在时保留空 Key，并由配置页提示补充。
3. 为提示词表增加 `audit_type`，现有记录标记为 `revision` 并全部停用。
4. 插入重新编写的初始审核提示词和修订审核提示词。
5. 为审核记录增加 `audit_type`。
6. 根据关联版本的 `version_type` 回填历史审核类型。
7. 新增按审核类型查找启用提示词和待处理审核的索引。
8. 不删除检查点表、检查点快照、旧提示词模型字段或历史 JSON 字段。

迁移前提供预检查，统计现有提示词、审核记录、无法关联版本的审核记录和当前模型配置来源。执行后验证两种启用提示词各一条、历史审核类型无空值、共用模型配置存在。

## 错误处理

- 共用模型配置不存在：任务失败并提示“未配置共用模型连接”。
- 对应审核类型没有启用提示词：任务失败并指出具体类型。
- 审核类型非法：创建任务时拒绝，Worker 不领取非法任务。
- DOCX 标题结构或目录无法提取：继续审核其他内容，并在模型输入中标记不可判断。
- 模型输出没有标准结论：保存 Markdown，状态为 `completed`，不伪造通过或不通过。

## 测试范围

### 后端

- 批次登记创建 `initial` 审核。
- 远程文件上传登记创建 `initial` 审核。
- 用户上传版本创建 `revision` 审核。
- 重试沿用原审核类型。
- Worker 为两种任务选择正确提示词。
- 两种提示词独立版本化和启用。
- 模型连接配置共用且 Key 不返回明文。
- 缺失模型配置或对应提示词时任务进入明确错误状态。
- 旧审核记录回填和历史结果查询不受影响。
- DOCX 标题与目录结构提取覆盖正常和不可提取场景。

### 前端

- 模型连接配置只显示一份。
- 两个提示词页签分别加载和保存。
- 页面不再请求或展示业务检查点。
- 审核详情和工作台正确显示审核类型。
- 报告列表、上传、预览、下载和审核状态轮询保持不变。

### 回归

- 现有报告版本和审核记录仍可查询。
- 历史 Markdown 和检查点快照仍可展示。
- 初始报告登记接口和用户上传接口的请求格式保持兼容。
- AI 对话仍使用对应报告版本和审核上下文。

## 发布顺序

1. 在非生产数据库执行预检查和迁移测试。
2. 生产发布前确认没有正在执行的审核并暂停审核 Worker。
3. 备份数据库并执行远端数据库迁移。
4. 部署并启动支持双审核类型的 API 和 Worker。
5. 配置共用模型连接并确认两套提示词各有一个启用版本。
6. 分别创建一条初始审核和修订审核进行验证。
7. 部署前端并验证配置页、报告详情和审核工作台。
8. 保留旧检查点数据和数据库备份作为回滚依据。

数据库迁移和生产部署属于独立写操作，实施完成后仍需用户分别确认执行。
